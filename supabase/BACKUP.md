# Бекъп и възстановяване

## Какво имаме

Два независими слоя. Единият не замества другия.

| | Къде | История | За какво помага |
|---|---|---|---|
| **Supabase Pro** (автоматичен) | вътре в Supabase | 7 дни | бърз откат при скорошна грешка |
| **GitHub Action** (наш) | GitHub artifacts, криптиран | 90 дни | оцелява проблем със самия Supabase акаунт; хваща грешки, забелязани късно |

Нашият тръгва всяка нощ в 02:30 UTC (04:30/05:30 бълг. време) и може да се пусне
ръчно от Actions → „Бекъп на базата" → Run workflow.

## Настройка (веднъж)

В GitHub → Settings → Secrets and variables → Actions:

| Secret | Откъде |
|---|---|
| `SUPABASE_DB_URL` | Supabase → Settings → Database → Connection string → **URI**, режим „Session". Паролата се вписва вътре в низа. |
| `BACKUP_PASSPHRASE` | Дълга парола, която **измисляш ти**. |

⚠️ **`BACKUP_PASSPHRASE` се пази и извън GitHub** — в мениджъра за пароли например.
Ако я загубиш, бекъпите стават безполезни: криптирани са симетрично и няма
как да се отворят без нея. GitHub не я показва обратно след записване.

## Възстановяване

### 1. Сваляне

GitHub → Actions → „Бекъп на базата" → отвори последното успешно пускане →
секция Artifacts → `db-backup-ГГГГ-ММ-ДД`.

### 2. Разкриптиране

```bash
gpg --decrypt backup-2026-08-20.sql.gz.gpg | gunzip > backup.sql
```

Пита за паролата (`BACKUP_PASSPHRASE`).

### 3. Проверка преди възстановяване

```bash
grep -c '^CREATE TABLE' backup.sql   # очаквани: 30+
grep -c '^COPY '        backup.sql   # секции с данни
head -50 backup.sql                  # че е валиден SQL, не съобщение за грешка
```

### 4. Възстановяване

**Първо на dev проекта, никога направо на prod.** Дъмпът съдържа `CREATE TABLE`
без `IF NOT EXISTS` — върху непразна база ще даде грешки за съществуващи обекти.

```bash
# В dev Supabase → Settings → Database → Connection string
psql "<connection-string-на-DEV>" -f backup.sql
```

Пълно възстановяване върху съществуваща база иска първо изчистване на схемата:

```sql
-- ВНИМАНИЕ: трие всичко в public. Само на dev, само ако си сигурен.
drop schema public cascade;
create schema public;
grant usage on schema public to anon, authenticated, service_role;
```

…и чак тогава `psql -f backup.sql`.

**Само една таблица** (по-честият случай — някой е изтрил данни):

```bash
# Изважда само нужната секция от дъмпа
sed -n '/^COPY public.crm_clients /,/^\\\.$/p' backup.sql > clients.sql
# После в SQL Editor: изчисти таблицата (ако трябва) и пусни clients.sql
```

### 5. След възстановяване на prod

```sql
NOTIFY pgrst, 'reload schema';
```

Иначе PostgREST продължава да вижда старата схема.

## Какво НЕ влиза в дъмпа

Само схемата `public`. Извън нея остават:

- **`auth.users`** — потребителите и паролите. Управляват се от Supabase; при
  пълна загуба на проекта хората се създават наново през Персонал.
- **Edge функции** (`swift-task`, `mobica-send`, `admin-create-user`) — кодът им
  е в репото (`supabase/functions/`), но се деплойват ръчно през Dashboard.
- **Secrets на edge функциите** (`REGDATA_*`, `MOBICA_*`) — пазят се в Supabase.
  Дръж копие извън него.

## Проверка на самия бекъп

Всяко пускане проверява автоматично, че дъмпът:
- не е подозрително малък,
- съдържа поне 20 таблици и 5 секции с данни,
- съдържа `crm_clients`, `crm_cell_values`, `crm_columns`, `crm_contacts`, `crm_staff`.

При провал workflow-ът пада и GitHub праща известие. Зелено пускане с празен
дъмп не може да се случи незабелязано.

**Веднъж на няколко месеца обаче си струва ръчно учение**: сваляш последния
бекъп, възстановяваш го на dev и влизаш да видиш, че данните са там. Само това
доказва, че веригата работи от край до край.
